# 027 Phase 2 database schema and migration

- **Tier:** 3 (schema mistakes are expensive to undo). **Suggested model:** Claude Opus.
- **Depends on:** 025. **Wave:** 2.

## Goal
Add the Phase 2 tables, enums and indexes to `src/db/schema.ts`, generate one migration, and revoke web access to grant abstracts.

## Why it matters
Every later Phase 2 task reads or writes these tables. Phase 2 only adds tables and appends enum values. It never rewrites existing rows (`docs/spec.md` section 5).

## Steps
1. **Enums.** Create the Phase 2 Postgres enums from the arrays added in Task 025. Check that `pnpm db:generate` emits `ALTER TYPE ... ADD VALUE` for appended values (`source_kind`, `llm_purpose`, `alias_source`), not a drop and recreate. If it does not, write that part of the migration by hand before it is merged, and say so in the PR.
2. **Tables.** Add every table in spec sections 5.2-5.4 with the columns, keys, foreign keys and indexes listed: `themes`, `tag_themes`, `company_themes`, `theme_weekly_stats`, `weekly_totals`, `funding_round_momentum`, `company_locations`, `derived_rebuilds`, `grant_projects`, `grant_project_texts`, `grant_participants`, `grant_taggings`, `event_record_sources`. Reuse the existing column helpers (`id()`, `timestamptz`, `moneyMinor`, `isoDate`, the 512-dimension vector).
3. **Constraints.**
   - `themes`: a check that `merged_into_id <> id`, and that `status = 'merged'` exactly when `merged_into_id` is set.
   - `theme_weekly_stats` and `weekly_totals`: `week_start` must be a Monday (`extract(isodow from week_start) = 1`).
   - Non-negative checks on counts and money.
   - `company_locations`: latitude and longitude are both null or both set.
   - `grant_project_texts.abstract` at most 1,500 characters.
4. **Typing.** `extractions.result` becomes `$type<ExtractionV1 | ExtractionV2>()`. Relations for the new tables.
5. **Roles.** In `scripts/sql/roles.sql`, revoke all web access to `grant_project_texts`, with a comment like the one for `source_item_texts`.
6. Run `pnpm db:generate`, then apply the migration twice to a local Postgres with pgvector (the second run must be a no-op).

## Tests and acceptance criteria
- `pnpm check` passes, and the CI migrations job applies the migration twice.
- `schema.test.ts` (PGlite) asserts:
  - every new table exists with its primary key;
  - appended enum values are accepted, and existing rows using old values are untouched;
  - a non-Monday `week_start` is rejected;
  - `tag_themes.theme_id` accepts null;
  - deleting an event cascades to `funding_round_momentum` and `event_record_sources`;
  - inserting a 512-dimension vector into `themes.centroid` works.
- The migration contains no `DROP`, no `ALTER COLUMN ... TYPE` and no `UPDATE` on existing tables.

## Out of scope
- Writing data into the new tables (later tasks), vector indexes (centroids are compared in code), any change to Phase 1 columns.
